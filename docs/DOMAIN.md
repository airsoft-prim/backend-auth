# Домен: сервис аутентификации Airsoft Prim

> Статус: **черновик**. Описание предметной области сервиса `backend-auth`.
> Маркеры состояния: `✅` — решено и подтверждено кодом, `🚧` — решение принято, реализация не завершена,
> `⏳` — решение принято, но отложено на будущие версии, `⬜` — открытый вопрос, требует решения
> владельца проекта.
>
> Назначение файла: полное описание домена. Краткая версия и правила работы с кодом — в `AGENTS.md`.

## 1. Назначение сервиса

`backend-auth` — единая точка правды о том, кто такой пользователь страйкбольного портала Airsoft Prim
и что ему разрешено. Сервис хранит учётные данные, аутентифицирует пользователя и выпускает токены,
по которым остальные сервисы портала опознают его без обращения к auth на каждый запрос.

Границы ответственности:

- Сервис отвечает за **идентичность и аутентификацию**, а не за прикладную логику портала.
- Сервис — владелец таблиц схемы `auth`: пользователи и всё, что описывает их учётные записи.
- Сервис публикует **публичные** ключи подписи; приватные ключи не покидают сервис.
- Авторизация на уровне конкретных ресурсов портала остаётся за сервисами-потребителями:
  они получают из токена идентификатор пользователя и роль и сами решают, что ему можно.

## 2. Место в экосистеме

```text
frontend ──► backend-auth          аутентификация: регистрация, вход, смена/сброс пароля
                  │
                  ├─► PostgreSQL   схема auth, учётные записи
                  ├─► Redis        кеш: публичные JWK, одноразовые токены, антибрутфорс
                  └─► JWKS         /.well-known/jwks.json

backend-api  ────┐
backend-media ───┴─► проверяют подпись JWT публичным ключом и опознают пользователя
```

Потребители токенов не ходят в auth на каждый запрос `⬜ (целевая схема)`: предполагается проверка
подписи JWT по публичному ключу из JWKS и извлечение субъекта/роли из самого токена.

Чем сервис **не** является: он не хранит пользовательский контент, не ведёт бизнес-логику портала,
не является UI-админкой.

## 3. Акторы и роли

| Актор              | Описание                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| Гость              | Незарегистрированный посетитель: может зарегистрироваться и войти.                               |
| Пользователь       | Участник портала с учётной записью.                                                              |
| Модератор          | Пользователь с расширенными правами (состав прав `⬜`).                                          |
| Администратор      | Управляет пользователями: роли, блокировки.                                                      |
| Сервис-потребитель | `backend-api`, `backend-media`, `frontend` и др.: проверяют токены, но пользователей не создают. |
| Внешний клиент     | OAuth2/OIDC-клиент — **планируется**, сейчас не поддерживается.                                  |

Системные роли `✅`: `admin`, `moderator`, `user` (`UserRole`, `src/general/enums.py`),
в БД — enum `auth.user_role`. Значения членов enum хранятся в БД через `values_callable=UserRole.values`.

Права ролей `⬜`: конкретный набор разрешений модератора и администратора не зафиксирован;
на данный момент роль — это признак в токене, а решение о доступе принимает сервис-потребитель.

## 4. Сущности и глоссарий

### Пользователь (учётная запись)

Единственная доменная сущность, реализованная сейчас `✅`. Таблица `auth.users`,
модель `User` (`src/providers/database/models.py`).

| Поле                        | Смысл                                                                                            | Статус |
| --------------------------- | ------------------------------------------------------------------------------------------------ | ------ |
| `id`                        | Суррогатный первичный ключ (`BigInteger`, `Identity`).                                           | `✅`   |
| `username`                  | Отображаемое имя, уникальное.                                                                    | `✅`   |
| `email`                     | Контакт и логин. Уникальность — регистронезависимая, через функциональный индекс `lower(email)`. | `✅`   |
| `pswd_hash`                 | Хеш пароля (bcrypt через `pwdlib[bcrypt]`).                                                      | `✅`   |
| `last_pswd_change`          | Когда пароль менялся в последний раз; `NULL`, если ещё ни разу.                                  | `✅`   |
| `system_role`               | Системная роль (`auth.user_role`).                                                               | `✅`   |
| `disabled` / `disabled_at`  | Блокировка аккаунта и её момент.                                                                 | `✅`   |
| `created_at` / `updated_at` | Метки времени, проставляет PostgreSQL (`now()`).                                                 | `✅`   |
| Подтверждение email         | Признак/дата подтверждения адреса.                                                               | `⏳`   |

Соглашения по данным `✅`:

- Пользователь не удаляется физически — блокируется (`disabled`, `disabled_at`).
- Метки времени только timezone-aware и заполняются БД, а не приложением.
- Имена constraints и индексов задаются единым `NAMING_CONVENTION`, чтобы миграции Alembic были стабильны.

### Токены

- **Access-токен** — единственный тип токена в v1: JWT с субъектом (пользователем), ролью и сроком
  действия. Проверяется потребителями офлайн по публичному ключу. Время жизни — **24 часа**. `🚧`
- **Подпись** — `EdDSA` на кривой Ed25519 (`PyJWT` + `cryptography`). В JOSE это `alg: EdDSA`,
  а в JWK — `kty: OKP`, `crv: Ed25519`.
- **Обязательные claims** — `⬜`: минимально нужны `sub`, `iat`, `exp`, `iss` (см. §10).
- **Отзыв** — `⬜`: выданный токен живёт все 24 часа, поэтому выход, блокировка и смена пароля
  его не аннулируют (см. §10).
- **Refresh-токен** — `⏳` отложен на будущие версии (§8): сейчас признан избыточным. Вместо обновления
  доступа пользователь входит заново.

### Ключи подписи

- **Приватный ключ подписи** — `keyfile` в контейнере сервиса; читает его `PrivateJWKRepository`
  (`src/domain/repositories/filesystem/`). В репозиторий и в образ ключ не попадает. `🚧` Бэкап keyfile —
  `⬜`: без него нельзя будет проверять выданные ранее токены.
- **Публичные JWK** складываются в Redis: эндпоинт `GET /.well-known/jwks.json` (RFC 7517) отдаёт набор
  из кеша, а не читает keyfile на каждый запрос. `🚧` Сейчас эндпоинт отдаёт пустой набор.
- **Ротация** ключей и одновременная публикация нескольких ключей (старый + новый) — `⬜`.

### Кеш (Redis)

Хранит состояние, которому не место в PostgreSQL. Зафиксировано: **публичные JWK** для JWKS `🚧`.
Открыто: одноразовые токены сброса пароля, счётчики попыток входа, отзыв выданных токенов — `⬜`
(состав и TTL ключей). Провайдер клиента реализован (`src/providers/cache/client.py`), но к эндпоинтам
пока не подключён.

### Аудит входов

События входа (кто, когда, с какого контекста) — требование к сервису; модель/таблица и срок хранения `⬜`.

## 6. Сценарии (жизненные циклы)

Ниже — целевое поведение; фактическое состояние реализации — раздел 5.

**Регистрация.** Гость указывает username, email и пароль. Проверяются уникальность username и email
(по email — регистронезависимо, поэтому индекс по `lower(email)`) и политики пароля и username (§7);
пароль превращается в bcrypt-хеш, создаётся учётная запись с ролью `user`. Подтверждение email — `⏳` (§8).

**Вход.** Пользователь приходит с email и паролем. Учётная запись ищется по `lower(email)`, пароль
сверяется с `pswd_hash`, заблокированному пользователю отказывается во входе. При успехе выпускается
access-токен на 24 часа, событие входа попадает в аудит. `🚧`

**Обновление токена.** `⏳` В v1 сценария нет: обновлять нечего, пока нет refresh-токенов (§8), —
по истечении срока пользователь входит заново.

**Выход.** `⏳` Пока токен нечем отозвать: выход означает удаление токена на клиенте, а сам токен
остаётся валидным до истечения суток. Нужен ли отзыв через Redis — `⬜` (§10).

**Смена пароля.** Пользователь подтверждает текущий пароль и задаёт новый по политике (§7): обновляются
`pswd_hash` и `last_pswd_change`. Что делать с уже выданными токенами — `⬜` (§10).

**Сброс пароля.** Запрос по email, одноразовый токен с коротким TTL в Redis, установка нового пароля.
Каким сервисом доставляется письмо и какой TTL — `⬜` (§10).

**Блокировка.** `disabled = true` и `disabled_at`. Заблокированный пользователь не входит заново, но
выданный ранее токен живёт до истечения 24 часов: нужен ли отзыв или дополнительная проверка статуса
на стороне потребителя — `⬜` (§10).

**Администрирование.** Администратор меняет роли и блокирует учётные записи через API. Как заводится
первый администратор — `⬜`.

## 7. Политики и требования

- **Пароли.** Хранятся только в виде bcrypt-хеша (`pwdlib[bcrypt]`, `bcrypt` 5.x), в открытом виде не
  логируются и не передаются никуда, кроме самого входа. Политика без излишней строгости: длина от 8
  до 72 байт, обязательны строчная и заглавная буквы, цифра и специальный символ. Требований менять
  пароль по расписанию нет. Верхние 72 байта — жёсткое ограничение bcrypt: более длинный пароль теперь
  не обрезается молча, а отвергается с `ValueError`, поэтому длина проверяется валидацией до хеширования.
  `passlib` сознательно не используется: он не поддерживается с 2020 года и ломается на `bcrypt >= 4.1`.
- **Username.** 3–50 символов, латиница, цифры, `_` и `-`, начинается с буквы; регистр сохраняется.
  Уникальность сейчас регистрозависимая (`UNIQUE` по `username`), в отличие от email — `⬜` (§10).
- **Ошибки аутентификации.** Сообщения клиенту не должны раскрывать, существует ли учётная запись и что
  именно не совпало (email или пароль). `⬜` Формулировки нужно зафиксировать при реализации входа.
- **Аудит против логов.** Логи приложения (`loguru`) — не аудит: события входа нужно хранить отдельно,
  с устойчивым сроком хранения. `⬜`
- **Секреты.** Приватный ключ подписи — `keyfile` в контейнере (в репозиторий и образ не попадает),
  пароли БД и Redis — в переменных окружения. `.env` в `.gitignore`.
- **Наблюдаемость.** Готовность сервиса определяется `/health/readiness`: сейчас проверяется только БД,
  проверка Redis помечена `TODO` в `src/api/health/routes.py`.

## 8. Roadmap

Планируемая, но не текущая функциональность. Решено отложить (`⏳`) до будущих версий:

- **Refresh-токены** — сейчас избыточны: суточного access-токена хватает. Возвращаться к вопросу, когда
  суток станет мало или понадобится отзывать доступ до истечения срока.
- **Подтверждение email** — в будущих версиях; пока регистрация не требует подтверждения адреса.

OAuth2.0 / OpenID Connect — когда до этого дойдёт:

- discovery-документ `/.well-known/openid-configuration`;
- стандартные grant'ы: `password`, `refresh_token`, `client_credentials`;
- регистрация и учёт внешних клиентов (client_id/client_secret, redirect_uri), scopes.

Ограничение сейчас: сервис аутентифицирует **только пользователей портала**, внешние клиенты не
поддерживаются. При этом текущие решения не должны закрывать путь к стандарту: формат токена, набор
claims и роутинг стоит держать совместимыми с OAuth2/OIDC.

## 9. Вне scope

- Прикладные домены портала (матчи, команды, контент) — это `backend-api`.
- Хранение и раздача медиа — `backend-media`.
- Пользовательский интерфейс — `frontend`.
- Права на конкретные ресурсы: потребитель получает из токена пользователя и роль и сам решает,
  что ему доступно.
- OAuth2/OIDC — roadmap, см. раздел 8.

## 10. Открытые вопросы

Требуют решения владельца проекта. Пока пункт не решён, агент не должен выбирать вариант самовольно —
решение фиксируется здесь или в задаче.

1. **Claims access-токена**: минимальный обязательный набор (`sub`, `iat`, `exp`, `iss`, роль, `jti`) и их
   имена.
2. **Отзыв доступа**: нужен ли отзыв выданных токенов (выход, блокировка, смена пароля) через Redis при
   сроке жизни токена 24 часа.
3. **Ключи подписи**: бэкап keyfile, частота ротации, сколько ключей публикуется в JWKS одновременно.
4. **Регистр username**: оставить регистрозависимую уникальность или сделать регистронезависимой, как email.
5. **Роли и права**: что именно разрешено модератору и администратору.
6. **Аудит**: состав событий, хранилище, срок хранения, работа с персональными данными (IP, user-agent).
7. **Антибрутфорс**: пороги, длительность блокировки, где считать попытки.
8. **Сброс пароля**: каким сервисом доставляется письмо, TTL одноразового токена.
9. **Bootstrap**: как создаётся первый администратор.
10. **Проверка Redis** в `/health/readiness` — тем более что в Redis лежат публичные JWK.
11. **Тестовое окружение**: как поднимаются PostgreSQL и Redis для тестов — в репозитории нет ни
    Dockerfile, ни docker-compose, а часть проверок без них не проходит.
