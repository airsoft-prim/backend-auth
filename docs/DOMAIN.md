# Домен: сервис аутентификации Airsoft Prim

> Статус документа: **черновик**.
> Назначение: полное описание предметной области сервиса `backend-auth`.
> Краткая версия и правила работы с кодом — `AGENTS.md`.

## 1. Введение

### 1.1. Назначение сервиса

`backend-auth` — единая точка правды о том, кто такой пользователь страйкбольного портала Airsoft Prim
и что ему разрешено. Сервис хранит учётные данные, аутентифицирует пользователя и выпускает токены,
по которым остальные сервисы портала опознают его без обращения к auth на каждый запрос.

### 1.2. Границы ответственности

- Сервис отвечает за **идентичность и аутентификацию**, а не за прикладную логику портала.
- Сервис — владелец таблиц схемы `auth`: пользователи и всё, что описывает их учётные записи.
- Сервис публикует **публичные** ключи подписи; приватные ключи не покидают сервис.
- Авторизация на уровне конкретных ресурсов портала остаётся за сервисами-потребителями: они получают
  из токена идентификатор пользователя и роль и сами решают, что ему можно.

### 1.3. Терминология

Ключевые слова **ДОЛЖЕН**, **НЕ ДОЛЖЕН**, **СЛЕДУЕТ**, **НЕ СЛЕДУЕТ**, **МОЖЕТ** и
**НЕОБЯЗАТЕЛЬНО** в этом документе и в документах `docs/API_*.md` означают требования в смысле
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119):

- **ДОЛЖЕН** — абсолютное требование: без него поведение считается несоответствующим.
- **НЕ ДОЛЖЕН** — абсолютный запрет.
- **СЛЕДУЕТ** — рекомендация: отклонение допустимо, но требует обоснования.
- **НЕ СЛЕДУЕТ** — не рекомендуется: отклонение допустимо, но требует обоснования.
- **МОЖЕТ** — допустимая возможность.
- **НЕОБЯЗАТЕЛЬНО** — значение допустимо опустить, поведение по умолчанию задано отдельно.

Ключевое слово согласуется с подлежащим предложения: **ДОЛЖЕН** принимает род и число подлежащего
(`Сервис ДОЛЖЕН…`, `Пароли ДОЛЖНЫ…`), а безличное **СЛЕДУЕТ** ставит исполнителя в дательный падеж
(`Сервису СЛЕДУЕТ…`).

### 1.4. Обозначения статуса

- `✅` — решено и подтверждено кодом.
- `🚧` — решение принято, реализация не завершена.
- `⏳` — решение принято, но отложено на будущие версии.
- `⬜` — открытый вопрос, требует решения владельца проекта.

## 2. Место в экосистеме

### 2.1. Взаимодействие

```text
frontend ──► backend-auth          аутентификация: регистрация, вход, смена/сброс пароля
                  │
                  ├─► PostgreSQL   схема auth, учётные записи
                  ├─► Redis        кеш: публичные JWK, одноразовые токены, антибрутфорс
                  └─► JWKS         /.well-known/jwks.json

backend-api  ────┐
backend-media ───┴─► проверяют подпись JWT публичным ключом и опознают пользователя
```

Потребителям токенов СЛЕДУЕТ опознавать пользователя без обращения к auth на каждый запрос: проверять
подпись JWT по публичному ключу из JWKS и извлекать субъект и роль из самого токена. Схема целевая —
`⬜`.

### 2.2. Что сервис не делает

Сервис НЕ ДОЛЖЕН хранить пользовательский контент, вести бизнес-логику портала или служить
UI-админкой.

## 3. Акторы и роли

### 3.1. Акторы

| Актор              | Описание                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| Гость              | Незарегистрированный посетитель: может зарегистрироваться.                                       |
| Пользователь       | Участник портала с учётной записью: может войти.                                                 |
| Модератор          | Пользователь с расширенными правами.                                                             |
| Администратор      | Управляет пользователями: роли, блокировки.                                                      |
| Сервис-потребитель | `backend-api`, `backend-media`, `frontend` и др.: проверяют токены, но пользователей не создают. |

### 3.2. Системные роли

Системные роли `✅`: `admin`, `moderator`, `user` (`UserRole`, `src/domain/enums.py`), в БД — enum
`auth.user_role`. Значения членов enum ДОЛЖНЫ храниться в БД через `values_callable=UserRole.values`.

Права ролей `✅`: сервис фиксирует только сами роли. Что именно разрешено каждой роли, решают
сервисы-потребители: роль попадает в токен claim'ом `srl`, и доступ определяют они сами.

## 4. Сущности и глоссарий

### 4.1. Пользователь (учётная запись)

Единственная доменная сущность, реализованная сейчас `✅`. Таблица `auth.users`,
сущность `User` (`src/domain/entities.py`), ORM-модель `UserModel` (`src/infrastructure/database/models.py`).

| Поле                        | Смысл                                                                                      | Статус |
| --------------------------- | ------------------------------------------------------------------------------------------ | ------ |
| `id`                        | Суррогатный первичный ключ (`BigInteger`, `Identity`).                                     | `✅`   |
| `username`                  | Отображаемое имя, уникальное.                                                              | `✅`   |
| `email`                     | Контакт для связи; логином не служит. Уникальность — регистронезависимая (`lower(email)`). | `✅`   |
| `pswd_hash`                 | Хеш пароля (Argon2id, `pwdlib[argon2]`).                                                   | `✅`   |
| `last_pswd_change`          | Когда пароль менялся в последний раз; `NULL`, если ещё ни разу.                            | `✅`   |
| `system_role`               | Системная роль (`auth.user_role`).                                                         | `✅`   |
| `disabled` / `disabled_at`  | Блокировка аккаунта и её момент.                                                           | `✅`   |
| `created_at` / `updated_at` | Метки времени, проставляет PostgreSQL (`now()`).                                           | `✅`   |

Соглашения по данным `✅`:

- Пользователь НЕ ДОЛЖЕН удаляться физически — он блокируется (`disabled`, `disabled_at`).
- Метки времени ДОЛЖНЫ быть timezone-aware и заполняться БД, а не приложением.
- Имена constraints и индексов ДОЛЖНЫ задаваться единым `NAMING_CONVENTION`, чтобы миграции Alembic
  были стабильны.
- Email обязателен для учётной записи: он служит каналом связи и адресом для сброса пароля (§6.6),
  а вход выполняется по username (§6.2).

### 4.2. Токены

Сервис выпускает два типа JWT, связанных идентификатором сессии `sid`:

- **Refresh-токен** — это и есть сессия пользователя: подписанный JWT, который владелец предъявляет
  сервису, чтобы продлить сессию и получить access-токен. Передаётся только в HTTP-only cookie
  (`refresh_token`), аудитория — сам сервис (`APP_NAME`), время жизни — **30 дней** по умолчанию
  (`SECURITY_REFRESH_TOKEN_TTL`). `✅`
- **Access-токен** — делегация доступа от имени открытой сессии: JWT с субъектом, ролью и сроком действия.
  Проверяется потребителями офлайн по публичному ключу, аудитория — портал (`APP_PROJECT`), время жизни —
  **24 часа** по умолчанию (`SECURITY_ACCESS_TOKEN_TTL`). Выдаётся **только** маршрутом `/auth/refresh`. `✅`

Управление сессиями пользователя (`/sessions/*`) выполняется от текущей сессии, то есть по refresh-токену;
access-токен для этого не используется.

- **Заголовок** — `✅`: `alg: EdDSA`, `typ` — тип токена (`access` или `refresh`) и `kid` — идентификатор
  ключа подписи, по которому потребитель находит публичный ключ в JWKS.
- **Подпись** — `EdDSA` на кривой Ed25519 (`PyJWT` + `cryptography`). В JOSE это `alg: EdDSA`,
  а в JWK — `kty: OKP`, `crv: Ed25519`.
- **Claims** — `✅` (общие для обоих типов, `src/domain/tokens.py`):
  - `iss` — издатель, `APP_NAME` (по умолчанию `Auth Server`);
  - `aud` — аудитория: `APP_PROJECT` у access-токена, `APP_NAME` у refresh-токена;
  - `sub` — Id пользователя строкой (в JWT `sub` всегда строка);
  - `iat` — момент выпуска, `exp` — момент истечения;
  - `jti` — идентификатор токена для отзыва;
  - `sid` — идентификатор сессии, к которой относится токен;
  - `srl` — необязательный claim только access-токена: системная роль пользователя (`admin`, `moderator`,
    `user`).
- **Выпуск и проверка** — `✅` `SignToken` и `VerifyToken` (`src/application/token.py`): первый подписывает
  токен приватным ключом из keyfile, второй выбирает публичный ключ по `kid` и проверяет подпись, `iss`,
  `aud`, срок действия, тип токена и наличие обязательных claims.
- **Отзыв** — `✅`: `RedisRevokedTokensRepository` хранит отозванные токены по ключу
  `token:<access|refresh>:revoked:<jti>`, а `RedisRevokedSessionsRepository` — отозванные сессии по ключу
  `session:revoked:<sid>`; TTL записи равен остатку срока жизни. `/auth/logout` отзывает сессию, а ротация
  в `/auth/refresh` — прежний refresh-токен. Проверка токена (`EnsureTokenActive`) сначала сверяется с
  отозванной сессией (`sid`), затем — с `jti` самого токена. Блокировка и смена пароля пока выданные
  токены не отзывают (§9).

### 4.3. Ключи подписи

- **Приватный ключ подписи** — `keyfile` в контейнере сервиса; в репозиторий и в образ он НЕ
  ДОЛЖЕН попадать. Читает и пишет его `FilePrivateJwkRepository` поверх объекта `FileSystem`
  (`src/infrastructure/filesystem/`): блокирующие вызовы файловой системы уходят в пул потоков, запись
  атомарная, права `0o600`. Репозиторий не хранит состояние: он живёт в рамках запроса и читает
  keyfile при каждом обращении, поэтому ротация видна сразу. Бэкап `keyfile` не нужен: при утере
  ключ просто генерируется заново. `✅`
- **Публичные JWK** складываются в Redis: эндпоинт `GET /.well-known/jwks.json` (RFC 7517) отдаёт набор
  из кеша, а не читает keyfile на каждый запрос. `✅` Набор публичных ключей собирает
  `CollectJwks` (`src/application/jwk.py`).
- **Ротация** ключей `✅`: ключ меняется по cron-правилу (`SECURITY_KEY_ROTATION_RULE`); в наборе JWKS
  одновременно живут новый ключ и ключи прошлых ротаций, пока не истечёт их TTL. TTL равен интервалу
  между ротациями и назначается ключу один раз: повторная ротация не продлевает срок ключей, у которых
  TTL уже есть.

### 4.4. Кеш (Redis)

Хранит состояние, которому не место в PostgreSQL. Зафиксировано: **публичные JWK** для JWKS `✅`,
**сессии пользователей** `✅` (`RedisSessionRepository`: JSON по ключу `session:<sid>` с TTL до `expires_at`
и индекс `session:user:<user_id>` для лимита активных сессий) и
**записи об активных сбросах пароля** `🚧` — запись «об активном сбросе» для адреса и запись по токену
из письма (хранится хеш токена). TTL записей и переход к антибрутфорсу — `⬜`. Счётчики попыток входа —
`⬜`. **Отозванные токены и сессии** — `✅`: `RedisRevokedTokensRepository` хранит ключ
`token:<access|refresh>:revoked:<jti>`, а `RedisRevokedSessionsRepository` — `session:revoked:<sid>`; TTL
записи равен остатку срока жизни, поэтому запись исчезает сама, когда токен или сессия всё равно истекли
бы. `/auth/logout` отзывает сессию, а проверка Bearer отклоняет токен отозванной сессии или отозванный
токен.
Провайдер клиента реализован (`src/infrastructure/cache/client.py`) и подключён к JWKS-эндпоинту: публичные
ключи он читает из отдельной БД `StorageNumber.KEYS`.

## 6. Сценарии (жизненные циклы)

Ниже — целевое поведение; фактическое состояние реализации — §5.

### 6.1. Регистрация

Гость указывает username, email и пароль. Сервис ДОЛЖЕН проверить уникальность username
(регистрозависимо) и email (регистронезависимо, поэтому индекс по `lower(email)`), а также политики
пароля и username (§7). Пароль ДОЛЖЕН храниться только как Argon2id-хеш. Создаётся учётная запись с ролью
`user`. Email обязателен: он нужен для связи и для сброса пароля (§6.6), хотя вход выполняется по
username (§6.2). Подтверждение email — `⏳` (§8). Реализовано `✅`: маршрут `POST /auth/register` отвечает
204 (`docs/API_AUTH.md` §4.1).

### 6.2. Вход

Пользователь приходит с логином (username) и паролем. Учётная запись ищется по `username`
(регистрозависимо, §7.2), пароль сверяется с `pswd_hash`; заблокированная учётная запись получает тот
же 401, что и несуществующая. При успехе сервис **открывает сессию**: создаёт запись сессии в Redis,
выпускает refresh-токен и кладёт его в HTTP-only cookie, а отвечает 204 без тела. Access-токен вход
НЕ выдаёт — его выпускает только `/auth/refresh` (§6.3). Аудит события входа пока не реализован (`⬜`). `✅`

### 6.3. Обновление токена

`✅` Маршрут `/auth/refresh` принимает refresh-токен из HTTP-only cookie, продлевает сессию (sliding
expiration) и выпускает новый access-токен для действий от имени сессии. Refresh-токен при этом
ротируется: прежний отзывается, а новый кладётся в cookie. Роль пользователя перечитывается из БД, чтобы
изменение роли отражалось в новом access-токене.

### 6.4. Выход

`✅` Маршрут `/auth/logout` принимает refresh-токен из HTTP-only cookie, отзывает сессию (`sid`) в Redis
и удаляет cookie; отвечает 204. Отзыв сессии делает недействительными все её токены: и refresh-токен,
и ранее выданные access-токены этой сессии. Другие сессии учётной записи действуют до истечения срока.

### 6.5. Смена пароля

Пользователь подтверждает текущий пароль и задаёт новый по политике (§7): обновляются `pswd_hash` и
`last_pswd_change`. Что делать с уже выданными токенами — `⬜` (§9).

### 6.6. Сброс пароля

Запрос по email: сервис заводит в Redis временную запись об активном сбросе и отправляет письмо со
ссылкой на страницу сброса фронтенда. Ссылка несёт одноразовый токен; страница возвращает его вместе с
новым паролем, после чего запись удаляется. Каким путём уходит письмо, какой TTL у записи и какой адрес
страницы подставляется в ссылку — `⬜` (§9).

### 6.7. Блокировка

`disabled = true` и `disabled_at`. Заблокированный пользователь не входит заново, но выданный ранее
токен живёт до истечения 24 часов: нужен ли отзыв или дополнительная проверка статуса на стороне
потребителя — `⬜` (§9).

### 6.8. Администрирование

Администратор меняет роли и блокирует учётные записи через API. Первый администратор заводится вручную,
через БД: отдельного способа его создания у сервиса нет.

### 6.9. Профиль владельца токена

`✅` `GET /auth/me` проверяет Bearer-токен, находит учётную запись по `sub` и отдаёт её данные: `id`,
`username`, `email`, `role`, `created_at`, `updated_at`. Хеш пароля, признак блокировки и служебные метки
не отдаются. Заблокированная учётная запись получает профиль, пока её токен действует: блокировка
закрывает только новый вход (§6.7). Если `sub` не числовой или учётная запись не найдена, владельца
токена идентифицировать нельзя, и запрос отклоняется.

## 7. Политики и требования

### 7.1. Пароли

Пароли ДОЛЖНЫ храниться только в виде Argon2id-хеша (`pwdlib[argon2]`, `argon2-cffi`); сервис НЕ
ДОЛЖЕН логировать пароль в открытом виде и НЕ ДОЛЖЕН передавать его никуда, кроме самого входа.
Политика без излишней строгости: длина от 8 до 72 символов; ДОЛЖНЫ присутствовать строчная и заглавная
буквы, цифра и специальный символ; классы символов — ASCII, как в POSIX: `[:lower:]`, `[:upper:]`,
`[:digit:]`, `[:punct:]`. Требований менять пароль по расписанию нет. Предела длины входа у Argon2id
нет, поэтому пароль хешируется целиком и проверять длину в байтах не нужно: верхние 72 символа — решение
сервиса, а не требование алгоритма. Параметры Argon2id — по умолчанию библиотеки.

### 7.2. Username

3–30 символов, латиница, цифры, `_` и `-`, начинается с буквы; регистр сохраняется. Уникальность
регистрозависимая (`UNIQUE` по `username`), в отличие от регистронезависимого email. Username служит
логином: по нему выполняется вход (§6.2), а email в этом качестве не используется.

### 7.3. Ошибки аутентификации

Сообщения клиенту НЕ ДОЛЖНЫ раскрывать, существует ли учётная запись и что именно не совпало (логин
или пароль). Тексты ошибок ДОЛЖНЫ быть на английском (`AGENTS.md` §7). `⬜` — точные формулировки нужно
зафиксировать при реализации входа.

### 7.4. Аудит

Логи приложения (`loguru`) — не аудит: события входа ДОЛЖНЫ храниться отдельно, с устойчивым сроком
хранения. `⬜`

### 7.5. Секреты

Приватный ключ подписи — `keyfile` в контейнере (в репозиторий и образ он НЕ ДОЛЖЕН попадать), пароли
БД и Redis — в переменных окружения. `.env` в `.gitignore`.

### 7.6. Наблюдаемость

Готовность сервиса определяется `/health/readiness`: проверяются БД (`SELECT 1`) и кеш (команда `PING`
в Redis); отказ любой из проверок даёт 503. Что именно проверяется и чего проба не видит —
`docs/API_HEALTH.md` (§4, §8).

## 8. Roadmap

Планируемая, но не текущая функциональность. Решено отложить (`⏳`) до будущих версий:

- **Подтверждение email** — в будущих версиях; пока регистрация не требует подтверждения адреса.

Ограничение сейчас: сервис аутентифицирует **только пользователей портала** и не является поставщиком
идентичности для сторонних приложений (§4.2): внешние клиенты и сторонние протоколы авторизации НЕ
поддерживаются.

## 9. Открытые вопросы

Требуют решения владельца проекта. Решённые пункты отмечены `✅` и остаются в списке ради нумерации
ссылок. Пока пункт не решён, агент НЕ ДОЛЖЕН выбирать вариант самовольно — решение фиксируется здесь или
в задаче.

1. **Claims access-токена** — `✅` решено: заголовок `alg`/`typ`/`kid`, обязательные claims `iss`, `aud`,
   `sub`, `iat`, `exp`, `jti` и необязательный `srl` (§4.2). `expires_in` в ответе на вход — срок жизни
   в секундах (`docs/API_AUTH.md` §8, п. 8).
1. **Отзыв доступа** — `✅` решено и реализовано для выхода: выданные токены отзываются через Redis,
   репозиторий блэклиста хранит `token:<access|refresh>:revoked:<jti>` с TTL, равным остатку срока жизни
   токена (§4.2, §4.4), а `/auth/logout` проверяет токен и записывает `jti`. Блокировка и смена пароля пока
   выданные токены не отзывают — это отдельное решение для этих сценариев.
1. **Аудит**: состав событий, хранилище, срок хранения, работа с персональными данными (IP, user-agent).
1. **Антибрутфорс**: пороги, длительность блокировки, где считать попытки.
1. **Сброс пароля**: каким путём уходит письмо, TTL записи об активном сбросе, адрес страницы сброса
   фронтенда и число одновременных активных сбросов на адрес.
1. **Тестовое окружение**: как поднимаются PostgreSQL и Redis для тестов — в репозитории есть
   `docker-compose.yaml` с профилями `dev` и `deploy`, но отдельного тестового профиля нет, а часть
   проверок без инфраструктуры не проходит.
1. **Контракт слоя `/auth`**: форма ответа на регистрацию, размещение смены и сброса пароля — разбор в
   `docs/API_AUTH.md` §8. Блокировка при входе отдаёт единый 401.
1. **Роль в access-токене** — `✅` решено: роль выпускается необязательным claim'ом `srl` (§4.2),
   потребители читают её из токена. Изменение роли не отзывает уже выданные токены: они действуют до
   истечения срока (см. п. 2).

> Файл живой: при изменении доменных правил обновляй `docs/DOMAIN.md` вместе с кодом,
> а краткое описание и правила работы — в `AGENTS.md`.
