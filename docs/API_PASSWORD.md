# API слоя `/password`: маршруты и схемы

> Статус: **черновик**. HTTP-контракт слоя `/password` сервиса `backend-auth`.
> Маркеры состояния: `✅` — решено и подтверждено кодом, `🚧` — решение принято, реализация не завершена,
> `⏳` — решение принято, но отложено на будущие версии, `⬜` — открытый вопрос, требует решения
> владельца проекта.
>
> Назначение файла: маршруты, схемы и коды ответов слоя паролей. Предметная область — `docs/DOMAIN.md`,
> контракт аутентификации — `docs/API_AUTH.md`, правила работы с кодом — `AGENTS.md`.

## 1. Назначение и состав слоя

Слой `/password` работает с паролем уже существующей учётной записи: смена по текущему паролю и сброс по
ссылке из письма. Регистрация, вход и выход — слой `/auth` (`docs/API_AUTH.md`).

| Маршрут                 | Назначение                                  | Состояние                                 |
| ----------------------- | ------------------------------------------- | ----------------------------------------- |
| `POST /password/change` | Смена пароля по текущему паролю             | `🚧` контракт объявлен, логика — заглушка |
| `POST /password/reset`  | Запрос сброса: письмо со ссылкой            | `🚧` контракт объявлен, логика — заглушка |
| `PATCH /password/reset` | Установка нового пароля по токену из ссылки | `🚧` контракт объявлен, логика — заглушка |

Смежные поверхности, которые в этот слой не входят:

| Поверхность                        | Где живёт                                                                           |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| Регистрация, вход и выход          | `POST /auth/register`, `POST /auth/login`, `POST /auth/logout` (`docs/API_AUTH.md`) |
| Шаблон политики пароля             | `PASSWORD_REQUIREMENTS` в `src/api/auth/schemas.py`, политика — `docs/DOMAIN.md` §7 |
| Страница сброса с формой пароля    | `frontend`, вне этого сервиса                                                       |
| Записи об активных сбросах в Redis | `⬜` не реализовано, устройство — §5                                                |
| Отправка письма                    | `⬜` не решено, каким путём (`docs/DOMAIN.md` §10.8)                                |
| Отзыв выданных access-токенов      | `⏳` отложено (`docs/DOMAIN.md` §10.2)                                              |

## 2. Соглашения

Общие для сервиса: JSON, время в UTC по RFC 3339, формат ошибки `{"detail": ...}`, тексты ошибок на
английском — `docs/API_AUTH.md` §2. Отличия слоя:

| Параметр        | Значение                                                                                      |
| --------------- | --------------------------------------------------------------------------------------------- |
| Базовый префикс | `/password`                                                                                   |
| Аутентификация  | Bearer-токен нужен только для `POST /password/change`; сброс подтверждается токеном из ссылки |
| Тег OpenAPI     | `Пароли`                                                                                      |

## 3. Схемы данных

Схемы объявлены в `src/api/password/schemas.py` и видны в Swagger UI (`/docs`) и ReDoc (`/redoc`).

### 3.1 `ChangePasswordRequestBody` — тело запроса на смену пароля

| Поле               | Тип    | Обязательное | Ограничения                               |
| ------------------ | ------ | ------------ | ----------------------------------------- |
| `current_password` | string | да           | Текущий пароль учётной записи             |
| `new_password`     | string | да           | 8–72 символа и политика пароля (см. §3.4) |

```json
{
  "current_password": "Old0!Pass",
  "new_password": "Str0ng!Pass"
}
```

### 3.2 `PasswordResetRequestBody` — тело запроса на сброс пароля

| Поле    | Тип    | Обязательное | Ограничения                   |
| ------- | ------ | ------------ | ----------------------------- |
| `email` | string | да           | Валидный email учётной записи |

```json
{
  "email": "user@example.ru"
}
```

### 3.3 `PasswordResetConfirmRequestBody` — тело подтверждения сброса

| Поле           | Тип    | Обязательное | Ограничения                               |
| -------------- | ------ | ------------ | ----------------------------------------- |
| `token`        | string | да           | Одноразовый токен из ссылки в письме      |
| `new_password` | string | да           | 8–72 символа и политика пароля (см. §3.4) |

```json
{
  "token": "one-time-token",
  "new_password": "Str0ng!Pass"
}
```

### 3.4 Политика нового пароля

Новый пароль проверяется тем же шаблоном, что и пароль при регистрации: `PASSWORD_REQUIREMENTS` из
`src/api/auth/schemas.py` (политика живёт в одном месте). Нужен хотя бы один символ каждого класса:
строчная буква, заглавная буква, цифра и специальный символ — классы ASCII, как в POSIX (`[:lower:]`,
`[:upper:]`, `[:digit:]`, `[:punct:]`). При несоответствии — 422 с сообщением
`Password does not meet the security requirements.` Длина проверяется по символам (8–72); предел bcrypt
в 72 байта пока никто не проверяет — `🚧`.

## 4. Маршруты

### 4.1 `POST /password/change` — смена пароля

Меняет пароль учётной записи, владелец которой подтвердил текущий пароль.

- Аутентификация: требуется Bearer-токен.
- Тело запроса: `ChangePasswordRequestBody`.
- Ответ 204: тело ответа отсутствует.
- Побочные эффекты: обновляются `pswd_hash` и `last_pswd_change` (`docs/DOMAIN.md` §6).
- Выданные ранее access-токены остаются действительными: отзыва нет (`docs/DOMAIN.md` §10.2).

| Код | Когда                                             | Тело              |
| --- | ------------------------------------------------- | ----------------- |
| 204 | Пароль изменён                                    | —                 |
| 400 | Текущий пароль не совпал с сохранённым            | `{"detail": ...}` |
| 401 | Токен доступа отсутствует или не принят           | `{"detail": ...}` |
| 422 | Тело не соответствует схеме, в том числе политике | Ошибки FastAPI    |
| 500 | Логика не реализована (заглушка)                  | —                 |

```bash
curl -X POST http://localhost:8000/password/change \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"current_password": "Old0!Pass", "new_password": "Str0ng!Pass"}'
```

Код ответа на несовпавший текущий пароль — решение `⬜` (§9, п. 1): это не отказ в аутентификации,
пользователь уже опознан по токену.

### 4.2 `POST /password/reset` — запрос сброса пароля

Принимает email учётной записи и запускает сброс: сервис заводит в Redis временную запись об активном
сбросе и ставит в отправку письмо со ссылкой на страницу сброса (устройство — §5).

- Аутентификация: не требуется.
- Тело запроса: `PasswordResetRequestBody`; email обязателен.
- Ответ 204: тело ответа отсутствует.
- Ответ одинаков для существующей и неизвестной учётной записи: иначе эндпоинт подсказывал бы, какие
  адреса зарегистрированы. Для неизвестного адреса письмо не отправляется, но ответ тот же.
- Побочные эффекты: запись в Redis и письмо; пароль при этом не меняется.

| Код | Когда                                      | Тело           |
| --- | ------------------------------------------ | -------------- |
| 204 | Запрос принят                              | —              |
| 422 | Тело не соответствует схеме                | Ошибки FastAPI |
| 429 | Слишком много запросов: `⬜` не реализован | —              |
| 500 | Логика не реализована (заглушка)           | —              |

```bash
curl -X POST http://localhost:8000/password/reset \
  -H "Content-Type: application/json" \
  -d '{"email": "user@example.ru"}'
```

### 4.3 `PATCH /password/reset` — подтверждение сброса

Принимает токен из ссылки в письме и новый пароль: проверяет запись об активном сбросе и устанавливает
пароль.

- Аутентификация: не требуется — право на смену даёт сам токен.
- Тело запроса: `PasswordResetConfirmRequestBody`.
- Ответ 204: тело ответа отсутствует.
- Токен одноразовый: после успешного подтверждения запись удаляется, и по той же ссылке пароль больше
  не сменить.
- Побочные эффекты: обновляются `pswd_hash` и `last_pswd_change` (`docs/DOMAIN.md` §6).

| Код | Когда                                                    | Тело              |
| --- | -------------------------------------------------------- | ----------------- |
| 204 | Пароль установлен                                        | —                 |
| 400 | Токен неизвестен, просрочен или уже использован          | `{"detail": ...}` |
| 422 | Тело не соответствует схеме, в том числе политике пароля | Ошибки FastAPI    |
| 500 | Логика не реализована (заглушка)                         | —                 |

```bash
curl -X PATCH http://localhost:8000/password/reset \
  -H "Content-Type: application/json" \
  -d '{"token": "one-time-token", "new_password": "Str0ng!Pass"}'
```

Метод `PATCH` выбран потому, что запрос меняет поле существующего ресурса (пароль учётной записи);
тело при этом несёт и токен, и новый пароль.

## 5. Сброс пароля со ссылкой в письме

В письме нет ни пароля, ни кода, который нужно перепечатывать: там ссылка вида

```text
https://portal.example.ru/reset-password?token=<одноразовый токен>
```

Ссылка ведёт **на страницу фронтенда**, а не на этот сервис: форма нового пароля — часть `frontend`,
сервис аутентификации остаётся JSON API и ничего не рисует. Токен при этом никуда не исчезает — это тот
же одноразовый секрет, что и в варианте с кодом, только его не набирают руками, а передают странице
в query-параметре. Без секрета в ссылке подтвердить владение адресом нельзя.

Поток целиком:

1. Пользователь отправляет `POST /password/reset` с email.
2. Сервис молча проверяет, есть ли такая учётная запись. Для неизвестного адреса он всё равно отвечает
   204 и письма не отправляет.
3. Для существующей учётной записи сервис генерирует криптостойкий случайный токен, не связанный с
   пользователем, сохраняет его хеш в Redis и ставит письмо в отправку.
4. Пользователь открывает ссылку; страница фронтенда читает `token` из query-параметра и показывает
   форму нового пароля.
5. Страница отправляет `PATCH /password/reset` с токеном и новым паролем.
6. Сервис хеширует пришедший токен, находит запись, проверяет срок, обновляет `pswd_hash` и
   `last_pswd_change` и удаляет запись: токен становится недействительным.

Записи в Redis (состав полей и TTL — `⬜`, §9):

| Ключ                              | Что хранит              | Зачем                                                                                                      |
| --------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------- |
| `pass-reset:${token_hash}`        | `user_id`, `created_at` | Найти запись по токену и проверить её срок. Хранится хеш, а не токен: выгрузка кеша не даёт готовых ссылок |
| `pass-reset:email:${email_lower}` | `${token_hash}`         | Запись «об активном сбросе» для адреса: новый запрос делает прежнюю ссылку недействительной                |

Что для этого нужно:

- **Адрес страницы сброса.** Сервису нужен базовый URL фронтенда (например,
  `APP_PASSWORD_RESET_URL=https://portal.example.ru/reset-password`) — иначе ссылку не собрать.
  Такой настройки пока нет: `⬜`.
- **Заголовок `Referrer-Policy: no-referrer` на странице сброса.** Токен приходит в query-параметре, а
  браузер по умолчанию отправляет адрес текущей страницы — вместе с токеном — в заголовке `Referer`
  всем сторонним ресурсам страницы: аналитике, шрифтам, CDN, картинкам. Чужого счётчика достаточно,
  чтобы ссылка с токеном осела в чужих логах. Требование адресовано `frontend`: заголовок ставится в
  ответе страницы или через `<meta name="referrer" content="no-referrer">`, сервис аутентификации
  на это повлиять не может.
- **Отправка письма.** Своего почтового клиента у сервиса нет. Варианты: складывать задание в Redis и
  отдавать отправку отдельному воркеру, звать сервис уведомлений или отправлять SMTP напрямую (последнее
  потребует новой зависимости). Решение — `⬜` (`docs/DOMAIN.md` §10.8).

Подводные камни:

- **Ссылку нельзя гасить при открытии.** Почтовые клиенты и антивирусы (Outlook Safe Links, Gmail)
  открывают ссылки заранее, чтобы проверить их, — если бы токен сгорал при переходе, у пользователя
  после клика ничего бы не работало. Поэтому одноразовость обеспечивает только `PATCH`, то есть явное
  действие пользователя.
- **Токен попадает в историю браузера, `Referer` и логи промежуточных прокси.** Отсюда короткий TTL,
  одноразовость и требование `Referrer-Policy: no-referrer` к странице сброса (см. выше).
- **Ответ на запрос сброса не различает адреса.** Иначе эндпоинт превращается в проверялку «какие email
  зарегистрированы».

## 6. Как контракт описан в коде

| Файл                           | Что содержит                                                                 |
| ------------------------------ | ---------------------------------------------------------------------------- |
| `src/api/password/__init__.py` | Экспорт `router` слоя                                                        |
| `src/api/password/routes.py`   | Маршруты `APIRouter(prefix="/password")`; тело — `raise NotImplementedError` |
| `src/api/password/schemas.py`  | Схемы запросов и `check_password_policy` — общая проверка политики           |
| `src/api/password/docs.py`     | Описания для OpenAPI (`RouteDocs`)                                           |
| `src/api/__init__.py`          | Подключение роутера слоя к `main_router`                                     |

Маршрут `change` объявлен с параметром-заглушкой `current_user: Any` — как в слое `/auth`
(`docs/API_AUTH.md` §5): определение пользователя по токену появится вместе с реализацией. Проверку
политики обе схемы с новым паролем берут из одной функции, а шаблон политики — из
`src/api/auth/schemas.py`, поэтому политика описана в одном месте.

## 9. Открытые вопросы

Требуют решения владельца проекта. Пока пункт не решён, поведение зафиксировано в коде как заглушка и
изменится вместе с реализацией.

1. **Коды отказа**: 400 для несовпавшего текущего пароля и для негодного токена сброса (предложено) или
   401 и 410 Gone соответственно?
2. **TTL записи о сбросе**: сколько живёт ссылка — 30 минут, час? От этого зависят запись в Redis и
   текст письма.
3. **Одна активная ссылка на адрес**: делать прежнюю ссылку недействительной при новом запросе
   (предложено) или разрешать несколько параллельных сбросов?
4. **Отправка письма**: очередь в Redis и отдельный воркер, сервис уведомлений или SMTP из этого сервиса
   (`docs/DOMAIN.md` §10.8).
5. **Адрес страницы сброса**: какой базовый URL фронтенда подставляется в ссылку и как называется
   query-параметр (`token`?).
6. **Проверка ссылки на странице**: нужен ли отдельный безопасный маршрут, чтобы страница заранее
   показывала «ссылка недействительна», не расходуя токен.
7. **Отзыв токенов**: должны ли выданные ранее access-токены переставать работать после сброса или смены
   пароля (`docs/DOMAIN.md` §10.2).
8. **Повтор пароля**: требовать ли, чтобы новый пароль отличался от прежнего.
9. **Антибрутфорс**: пороги и код 429 на запросы сброса (`docs/DOMAIN.md` §10.7).
10. **Размещение слоя**: остаётся ли `/password` или переезжает под `/auth/password`
    (`docs/API_AUTH.md` §8, п. 6).
11. **Длина в байтах**: предел bcrypt в 72 байта пока не проверяется — общий вопрос с `/auth`.
