# API слоя `/auth`: маршруты и схемы

> Статус документа: **черновик**. HTTP-контракт слоя `/auth` сервиса `backend-auth`.
> Предметная область — `docs/DOMAIN.md`; правила работы с кодом — `AGENTS.md`.
> Ключевые слова (ДОЛЖЕН/СЛЕДУЕТ/МОЖЕТ) и маркеры статуса описаны в `docs/DOMAIN.md` §1.3, §1.4.

## 1. Назначение и состав слоя

Слой `/auth` — точка входа для аутентификации пользователей портала: регистрация, вход и выход. Слой
отвечает за идентичность, но не за права на ресурсы портала: потребители токена решают это сами, читая
данные пользователя из JWT (`docs/DOMAIN.md` §1).

### 1.1. Маршруты слоя

| Маршрут               | Назначение                                | Состояние                                     |
| --------------------- | ----------------------------------------- | --------------------------------------------- |
| `POST /auth/register` | Создание учётной записи                   | `✅` работает: запись в `auth.users`          |
| `POST /auth/login`    | Проверка учётных данных и открытие сессии | `✅` работает: вход и refresh-токен в cookie  |
| `POST /auth/refresh`  | Выдача access-токена по refresh-токену    | `✅` работает: ротация и выпуск access-токена |
| `POST /auth/logout`   | Завершение сессии                         | `✅` работает: отзыв `sid` в Redis            |
| `GET /auth/me`        | Профиль владельца токена                  | `✅` работает: учётная запись по `sub`        |

Профиль владельца токена (`GET /auth/me`) — аналог `userinfo` в OIDC: клиент получает данные
учётной записи, не разбирая токен самостоятельно.

### 1.2. Смежные поверхности

Следующие поверхности в этот слой не входят:

| Поверхность                          | Где живёт                                                  |
| ------------------------------------ | ---------------------------------------------------------- |
| Публичные ключи подписи токенов      | `GET /.well-known/jwks.json` (`src/interface/well_known/`) |
| Смена и сброс пароля                 | `⬜` отдельный слой, заготовка `src/interface/password/`   |
| Администрирование ролей и блокировок | `⬜` не реализовано                                        |

## 2. Соглашения

| Параметр        | Значение                                                                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------------------ |
| Базовый префикс | `/auth`; в dev-окружении сервис слушает `http://localhost:8000`                                                    |
| Формат обмена   | JSON: `Content-Type: application/json; charset=utf-8`                                                              |
| Аутентификация  | Refresh-токен в HTTP-only cookie `refresh_token` для защищённых маршрутов auth                                     |
| Токен           | JWT, подпись `EdDSA` (Ed25519), срок жизни 5 минут по умолчанию (`SECURITY_ACCESS_TOKEN_TTL`, `docs/DOMAIN.md` §4) |
| Формат ошибки   | Объект `message`, `details`; у отказа валидации (422) — `detail` со списком ошибок FastAPI                         |
| Время           | UTC, формат RFC 3339                                                                                               |
| Идемпотентность | `GET /auth/me` идемпотентен; повторная регистрация — 500                                                           |
| CORS            | `⬜` не настроен: браузерный frontend с другого origin пока не сможет обратиться к сервису                         |

Тело запроса и ответа ДОЛЖНО быть валидным JSON. Аутентифицированные маршруты принимают refresh-токен в cookie и проверяют его сессию. Тексты ошибок ДОЛЖНЫ быть на английском (`AGENTS.md` §7).

## 3. Схемы данных

Схемы объявлены в `src/interface/auth/schemas.py`. Тела запросов и `AccessToken` привязаны к маршрутам и видны
в OpenAPI (Swagger UI `/docs`, ReDoc `/redoc`); `UserData` — модель ответа `GET /auth/me`, см. §3.4.

### 3.1. `RegisterRequestBody` — тело запроса на регистрацию

| Поле       | Тип    | Обязательное | Ограничения                                                                    |
| ---------- | ------ | ------------ | ------------------------------------------------------------------------------ |
| `username` | string | да           | 3–30 символов, начинается с латинской буквы, далее латиница, цифры, `_` и `-`  |
| `email`    | string | да           | Валидный email; контакт для связи, для входа НЕ используется                   |
| `password` | string | да           | 8–72 символа; хотя бы одна строчная буква, заглавная буква, цифра и спецсимвол |

```json
{
  "username": "stalker_2010",
  "email": "user@airsoft-prim.ru",
  "password": "Str0ng!Pass"
}
```

Email в теле регистрации обязателен, но логином не служит: адрес нужен для связи и для сброса пароля
(`docs/API_PASSWORD.md`), а вход выполняется по `username` (§3.2, `docs/DOMAIN.md` §6.2).

Политику пароля проверяет валидатор схемы `RegisterRequestBody.validate_password` — одно регулярное
выражение `PASSWORD_REQUIREMENTS` с классами символов в нотации POSIX: `[:lower:]`, `[:upper:]`,
`[:digit:]` и `[:punct:]`. При несоответствии сервис ДОЛЖЕН вернуть 422 с общим сообщением
`Password does not meet the security requirements.`: оно НЕ ДОЛЖНО раскрывать, какой именно класс
символов отсутствует. Классы — ASCII, как в POSIX: пароль без латинских букв требованиям не отвечает. На
`LoginRequestBody` валидатор НЕ ДОЛЖЕН распространяться: вход не должен отклонять пароли, заданные до
включения политики. Длина ограничена символами (8–72): пароли хеширует Argon2id, у которого предела длины
входа нет, — поэтому отдельной проверки в байтах (как у bcrypt) не требуется (`docs/DOMAIN.md` §7.1).

### 3.2. `LoginRequestBody` — тело запроса на вход

| Поле       | Тип    | Обязательное | Смысл                |
| ---------- | ------ | ------------ | -------------------- |
| `username` | string | да           | Логин учётной записи |
| `password` | string | да           | Пароль               |

Email в теле входа не принимается: адрес — контакт для связи, а не логин (`docs/DOMAIN.md` §6.2). К
`username` применяется та же политика, что и при регистрации (§3.1): иначе вход отклонял бы логины,
которые сервис принимал при регистрации.

### 3.3. `AccessToken` — ответ с токеном

| Поле           | Тип    | Значение                           |
| -------------- | ------ | ---------------------------------- |
| `access_token` | string | Подписанный JWT (алгоритм `EdDSA`) |
| `token_type`   | string | Всегда `Bearer`                    |
| `expires_in`   | int    | Срок жизни токена в секундах       |

Поля `access_token` и `token_type` совпадают с ответом на выдачу токена в OAuth2 (RFC 6749 §5.1), чтобы
при добавлении OIDC не пришлось менять контракт клиентов. `expires_in` содержит срок жизни токена в
секундах, как требует RFC 6749 §5.1. Срок жизни — 5 минут по умолчанию, настраивается
`SECURITY_ACCESS_TOKEN_TTL` (`docs/DOMAIN.md` §4). Этот ответ отдаёт только `POST /auth/refresh` (§4.3);
refresh-токен передаётся отдельно, в HTTP-only cookie, и в тело ответа не попадает.

### 3.4. `UserData` — данные учётной записи

| Поле         | Тип      | Смысл                                 |
| ------------ | -------- | ------------------------------------- |
| `id`         | int      | Идентификатор учётной записи          |
| `username`   | string   | Логин учётной записи                  |
| `email`      | string   | Адрес электронной почты               |
| `role`       | string   | Роль: `admin`, `moderator` или `user` |
| `created_at` | datetime | Момент создания учётной записи (UTC)  |
| `updated_at` | datetime | Момент последнего обновления (UTC)    |

Схема описывает учётную запись так, как её видит владелец; набор полей ограничен тем, что сервис
действительно хранит. Поле роли в схеме называется `role`, а в ORM-модели — `system_role`; при сборке
ответа схема читает ORM-поле через `validation_alias`. Хеш пароля, признак блокировки и служебные метки в
данные учётной записи попадать НЕ ДОЛЖНЫ.

`UserData` возвращает `GET /auth/me` (§4.5). Маршрут регистрации отвечает 204 без тела (§4.1), поэтому
профиль созданной учётной записи в ответе регистрации не появляется.

### 3.5. Тело ошибки

Единой схемы нет: ошибки приложения отдают объект `message`/`details`, а валидация FastAPI (422) —
`detail` со списком ошибок.

| Поле      | Тип             | Смысл                                         |
| --------- | --------------- | --------------------------------------------- |
| `message` | string          | Краткое описание ошибки                       |
| `details` | string          | Детали, безопасные для показа клиенту         |
| `detail`  | string или list | Тело 422 от FastAPI: строка или список ошибок |

Сам сервис отвечает объектом (401, 403, 409, 500), отказ валидации (422) — список объектов FastAPI с
полями `type`, `loc`, `msg`, `input`. Отсутствие refresh-токена обрабатывается общим обработчиком
`UserAuthorizationError`: 401 с `WWW-Authenticate: Bearer` и телом `message`/`details`. Тексты ошибок
ДОЛЖНЫ быть на английском (`AGENTS.md` §7).

Ошибки безопасности (`SecurityError`) обрабатываются общими обработчиками приложения:
невалидный, просроченный или неподписанный токен даёт 403, а отказ выпуска токена (например,
недоступный keyfile) — 500. Тело этих ответов — `message` и `details`; внутренняя причина отказа
выпуска в ответ не попадает. Ошибки входа (`UserIdentificationError`, `UserAuthenticationError`)
отдают 401 с заголовком `WWW-Authenticate: Bearer`.

```json
{
  "message": "Authorization failed.",
  "details": "Provided credentials are invalid."
}
```

Точные формулировки пока не зафиксированы: `⬜` (см. §8, п. 3).

## 4. Маршруты

### 4.1. `POST /auth/register` — регистрация

Создаёт учётную запись портала.

- Аутентификация: не требуется.
- Тело запроса: `RegisterRequestBody`.
- Ответ 204: тело пустое — профиль созданной учётной записи не отдаётся (§3.4, §8, п. 1).
- Побочные эффекты: запись в `auth.users`, роль `user`, `pswd_hash` — Argon2id-хеш пароля.
- Логин и адрес проверяются на занятость до записи, роль `user` проставляет сама БД (значение по умолчанию
  колонки `system_role`), поэтому приложение её не передаёт.
- Подтверждение email не требуется (`⏳`, `docs/DOMAIN.md` §8).

| Код | Когда                                                    | Тело               |
| --- | -------------------------------------------------------- | ------------------ |
| 204 | Учётная запись создана                                   | —                  |
| 409 | `username` или `email` уже заняты                        | Тело ошибки (§3.5) |
| 422 | Тело не соответствует схеме, в том числе политике пароля | Ошибки FastAPI     |
| 500 | Отказ БД                                                 | —                  |

```bash
curl -X POST http://localhost:8000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username": "stalker_2010", "email": "user@airsoft-prim.ru", "password": "Str0ng!Pass"}'
```

Ответ 204 тела не несёт: профиль созданной учётной записи не возвращается.

Занятые учётные данные сервис отвергает ошибкой `UserAlreadyExistsError` с английской причиной
(`Username is already taken.` или `Email is already taken.`); общий обработчик приложения переводит её
в 409, поэтому маршрут сам коды не транслирует. Уникальность окончательно держат констрейнты БД
(`UNIQUE` по `username` и индекс по `lower(email)`): параллельные регистрации одного логина вторую
учётную запись не создадут.

Токен регистрация НЕ ДОЛЖНА выдавать: клиент входит отдельным запросом. Выдавать токен сразу (автологин)
— открытый вопрос `⬜` (§8, п. 1).

### 4.2. `POST /auth/login` — вход

Проверяет логин и пароль и открывает сессию.

- Аутентификация: не требуется.
- Тело запроса: `LoginRequestBody`.
- Ответ 204: тело пустое; refresh-токен приходит в HTTP-only cookie `refresh_token`.
- Побочные эффекты: создаётся сессия (`sid`) в Redis, событие входа должно попадать в аудит
  (`⬜`, `docs/DOMAIN.md` §9.3).
- Ограничения на число сессий нет: новый вход не закрывает ранее открытые сессии.
- Учётная запись ищется по `username` (точное совпадение: уникальность регистрозависима,
  `docs/DOMAIN.md` §7.2); пароль сверяется с `pswd_hash`.
- Access-токен вход НЕ выдаёт: его выпускает только `POST /auth/refresh` (§4.3).
- Признак блокировки (`disabled`) проверяется: заблокированная учётная запись получает тот же 401,
  что и несуществующая, — клиент не узнаёт, что пара логин/пароль верна.
- Неудачные попытки входа не блокируют учётную запись; глобальный лимит запросов по IP действует
  независимо от результата аутентификации.
- Сообщение об ошибке НЕ ДОЛЖНО раскрывать, существует ли учётная запись и что именно не совпало.

| Код | Когда                                                   | Тело               |
| --- | ------------------------------------------------------- | ------------------ |
| 204 | Сессия открыта                                          | —                  |
| 401 | Неверный логин или пароль; учётная запись заблокирована | Тело ошибки (§3.5) |
| 422 | Тело не соответствует схеме                             | Ошибки FastAPI     |
| 429 | Лимит запросов по IP превышен                           | Тело ошибки (§3.5) |
| 500 | Отказ БД, Redis или выпуска refresh-токена              | Тело ошибки (§3.5) |

```bash
curl -X POST http://localhost:8000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username": "stalker_2010", "password": "Str0ng!Pass"}'
```

Ответ 204 тела не несёт: refresh-токен кладётся в HTTP-only cookie `refresh_token`, после чего клиент
вызывает `/auth/refresh` (§4.3), чтобы получить access-токен.

Блокировка и неверные учётные данные неразличимы для клиента: оба случая дают 401 с одинаковым телом
и `WWW-Authenticate: Bearer`.

### 4.3. `POST /auth/refresh` — выдача access-токена

Продлевает сессию и выпускает новый access-токен.

- Аутентификация: refresh-токен из HTTP-only cookie `refresh_token`.
- Тело запроса: нет.
- Ответ 200: `AccessToken`.
- Refresh-токен проверяется `VerifyToken`; сессия (`sid`) продлевается (sliding expiration), прежний
  refresh-токен отзывается (ротация), а новый кладётся в cookie.
- Роль пользователя перечитывается из БД, чтобы новый access-токен отражал актуальную роль.
- Отсутствие cookie даёт 401, недействительный, просроченный или отозванный refresh-токен — 403.

| Код | Когда                                            | Тело               |
| --- | ------------------------------------------------ | ------------------ |
| 200 | Access-токен выпущен                             | `AccessToken`      |
| 401 | Cookie отсутствует                               | Тело ошибки (§3.5) |
| 403 | Refresh-токен недействителен, просрочен, отозван | Тело ошибки (§3.5) |
| 500 | Отказ БД, Redis или выпуска токенов              | Тело ошибки (§3.5) |

```bash
curl -X POST http://localhost:8000/auth/refresh \
  -H "Cookie: refresh_token=<refresh_token>"
```

```json
{
  "access_token": "eyJhbGciOiJFZERTQSIsImtpZCI6ImF1dGgtMjAyNi0wOSJ9...",
  "token_type": "Bearer",
  "expires_in": 300
}
```

Повторное использование уже отозванного (ротированного) refresh-токена отклоняется: старый токен
помечается отозванным до конца срока действия.

### 4.4. `POST /auth/logout` — выход

Завершает сессию пользователя.

- Аутентификация: refresh-токен из HTTP-only cookie `refresh_token`.
- Тело запроса: нет.
- Ответ 204: тело ответа отсутствует; cookie `refresh_token` удаляется.
- Refresh-токен проверяется `VerifyToken`; сессия (`sid`) помечается отозванной в Redis до конца срока
  действия. Отозванная сессия больше не даёт доступа к auth. Уже выпущенный access-токен
  остаётся действительным при автономной проверке другими сервисами до своего истечения.
- Отсутствие cookie даёт 401 с `WWW-Authenticate: Bearer`. Недействительный, просроченный или
  отозванный refresh-токен даёт 403 через общий обработчик ошибок безопасности (§3.5).

| Код | Когда                                    | Тело               |
| --- | ---------------------------------------- | ------------------ |
| 204 | Выход выполнен                           | —                  |
| 401 | Cookie отсутствует                       | Тело ошибки (§3.5) |
| 403 | Токен недействителен, просрочен, отозван | Тело ошибки (§3.5) |
| 500 | Отказ Redis при записи или проверке      | Тело ошибки (§3.5) |

```bash
curl -X POST http://localhost:8000/auth/logout \
  -H "Cookie: refresh_token=<refresh_token>"
```

Выход отзывает только предъявленную сессию. Другие сессии той же учётной записи остаются
действительными до истечения своего срока.

### 4.5. `GET /auth/me` — профиль владельца токена

Возвращает данные учётной записи владельца активной сессии.

- Аутентификация: refresh-токен в HTTP-only cookie `refresh_token`.
- Тело запроса: нет.
- Ответ 200: `UserData`.
- `sub` токена приводится к числовому Id, по нему `GetUser` читает учётную запись.
- В ответ попадают только `id`, `username`, `email`, `role`, `created_at` и `updated_at`; хеш пароля,
  признак блокировки и служебные метки не отдаются.
- Заблокированная учётная запись получает профиль: блокировка закрывает новый вход, но не отзывает уже
  выданный токен (`docs/DOMAIN.md` §6.7).
- Отсутствие cookie даёт 401 с `WWW-Authenticate: Bearer`.
  Недействительный, просроченный или отозванный токен даёт 403. Если `sub` не числовой или учётная запись
  не найдена, ответ — 403 или 401 соответственно: владельца токена идентифицировать нельзя.

| Код | Когда                                                          | Тело               |
| --- | -------------------------------------------------------------- | ------------------ |
| 200 | Профиль получен                                                | `UserData`         |
| 401 | Cookie отсутствует; учётная запись не найдена                  | Тело ошибки (§3.5) |
| 403 | Токен недействителен, просрочен, отозван или `sub` не числовой | Тело ошибки (§3.5) |
| 500 | Отказ БД, Redis или проверки токена                            | Тело ошибки (§3.5) |

```bash
curl http://localhost:8000/auth/me \
  -H "Cookie: refresh_token=<refresh_token>"
```

```json
{
  "id": 42,
  "username": "stalker_2010",
  "email": "user@airsoft-prim.ru",
  "role": "user",
  "created_at": "2026-09-01T12:00:00Z",
  "updated_at": "2026-09-02T13:30:00Z"
}
```

Профиль отдаётся только владельцу токена: маршрут не принимает Id пользователя и не позволяет читать
чужие учётные записи.

## 5. Как контракт описан в коде

| Файл                            | Что содержит                                                                     |
| ------------------------------- | -------------------------------------------------------------------------------- |
| `src/interface/auth/routes.py`  | Маршруты `APIRouter(prefix="/auth")`; регистрация, вход, refresh, выход, профиль |
| `src/interface/auth/deps.py`    | Сборка use case; refresh-токен из cookie                                         |
| `src/interface/auth/schemas.py` | Схемы запросов и ответов этого документа                                         |
| `src/interface/auth/docs.py`    | Описания для OpenAPI (`RouteDocs`)                                               |
| `src/application/token.py`      | `SignToken`, `VerifyToken`, `Authorize`, ротация и отзыв токенов и сессий        |
| `src/application/auth.py`       | Регистрация, профиль, открытие и обновление сессии                               |
| `src/interface/__init__.py`     | Подключение роутера слоя к `main_router`                                         |

Для защищённых маршрутов auth refresh-токен извлекается из cookie; проверяются подпись,
назначение, срок, отзыв токена и состояние принадлежащей пользователю сессии. `get_current_user`
загружает владельца сессии. При отсутствии cookie общий обработчик возвращает 401.

Регистрацию обслуживают `RegisterUser` и репозиторий учётных записей: маршрут передаёт сервису логин,
адрес и пароль, сервис проверяет занятость и хеширует пароль перед записью. Хешер паролей (Argon2id)
общий для сервиса (`src/adapters/crypto/hasher.py`).

Вход обслуживает `OpenUserSession`: проверяет пароль, открывает сессию через `CreateSession`
и подписывает refresh-токен через `SignToken`. Refresh обслуживают `RotateRefreshToken`
(продление сессии и отзыв прежнего refresh-токена) и `IssueTokenPair` (выпуск пары access + refresh).
Выход обслуживает `RevokeSession`: помечает сессию отозванной по ключу `session:revoked:<sid>` с TTL до
конца срока действия.

## 7. Сводка кодов ответов

| Код | Когда                                                          | Маршруты                           |
| --- | -------------------------------------------------------------- | ---------------------------------- |

| 200 | Профиль получен                                                | `me`                               |
| 204 | Учётная запись создана                                         | `register`                         |

## 8. Открытые вопросы

Требуют решения владельца проекта. Пока пункт не решён, фактическое поведение описано в §4–§6 и может
отличаться от целевого.

1. **Ответ на регистрацию**: нужен ли профиль в ответе — сейчас 204 без тела — или профиль вместе с
   access-токеном, чтобы клиенту не требовался отдельный вход?
1. **Заблокированная учётная запись** — `✅` решено: единый 401, чтобы не подтверждать, что пара
   логин/пароль верна. Проверка `disabled` выполняется при входе.
1. **Формулировки ошибок** — `✅` формат зафиксирован: `message` и `details`, для 422 — `detail`.
   Осталось зафиксировать точные английские тексты для 401 (`docs/DOMAIN.md` §7). Трансляция
   `UserAlreadyExistsError` → 409 реализована в общем обработчике.
1. **Антибрутфорс**: пороги и окно блокировки (`docs/DOMAIN.md` §9.4). Код 429 отдаёт middleware
   ограничения частоты запросов (фиксированное окно по IP), а не блокировка учётной записи.
1. **Размещение паролей**: смена и сброс — `/auth/password/*` или отдельный слой `/password` (заготовка
   `src/interface/password/` уже есть)?
1. **CORS**: разрешить ли браузерному frontend обращаться к сервису с другого origin и с какими
   правилами.
1. **Версионирование**: оставить пустой префикс как сейчас или добавить версию (`/v1/auth/...`) до
   появления внешних потребителей API.
1. **`expires_in` в ответе на refresh** — `✅` решено: передаётся срок жизни access-токена в секундах,
   как описывает RFC 6749 §5.1.
