# API слоя `/auth`: маршруты и схемы

> Статус документа: **черновик**. HTTP-контракт слоя `/auth` сервиса `backend-auth`.
> Предметная область — `docs/DOMAIN.md`; правила работы с кодом — `AGENTS.md`.
> Ключевые слова (ДОЛЖЕН/СЛЕДУЕТ/МОЖЕТ) и маркеры статуса описаны в `docs/DOMAIN.md` §1.3, §1.4.

## 1. Назначение и состав слоя

Слой `/auth` — точка входа для аутентификации пользователей портала: регистрация, вход и выход. Слой
отвечает за идентичность, но не за права на ресурсы портала: потребители токена решают это сами, читая
данные пользователя из JWT (`docs/DOMAIN.md` §1).

### 1.1. Маршруты слоя

| Маршрут               | Назначение                              | Состояние                                 |
| --------------------- | --------------------------------------- | ----------------------------------------- |
| `POST /auth/register` | Создание учётной записи                 | `✅` работает: запись в `auth.users`      |
| `POST /auth/login`    | Проверка учётных данных и выдача токена | `✅` работает: вход и выпуск токена       |
| `POST /auth/logout`   | Завершение сессии                       | `🚧` контракт объявлен, логика — заглушка |

Профиль владельца токена (`GET /auth/me`) — `⏳` отложен: маршрут убран из контракта и вернётся вместе с
реализацией. В OIDC ему соответствует `userinfo`.

### 1.2. Смежные поверхности

Следующие поверхности в этот слой не входят:

| Поверхность                          | Где живёт                                            |
| ------------------------------------ | ---------------------------------------------------- |
| Публичные ключи подписи токенов      | `GET /.well-known/jwks.json` (`src/api/well_known/`) |
| Смена и сброс пароля                 | `⬜` отдельный слой, заготовка `src/api/password/`   |
| Администрирование ролей и блокировок | `⬜` не реализовано                                  |
| Обновление токена (refresh)          | `⏳` отложено (`docs/DOMAIN.md` §8)                  |

## 2. Соглашения

| Параметр        | Значение                                                                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------------------ |
| Базовый префикс | `/auth`; в dev-окружении сервис слушает `http://localhost:8000`                                                    |
| Формат обмена   | JSON: `Content-Type: application/json; charset=utf-8`                                                              |
| Аутентификация  | Заголовок `Authorization: Bearer <access_token>`, схема OpenAPI `HTTPBearer`                                       |
| Токен           | JWT, подпись `EdDSA` (Ed25519), срок жизни 24 часа по умолчанию (`SECURITY_ACCESS_TOKEN_TTL`, `docs/DOMAIN.md` §4) |
| Формат ошибки   | Объект `message`, `details`; у отказа валидации (422) — `detail` со списком ошибок FastAPI                         |
| Время           | UTC, формат RFC 3339                                                                                               |
| Идемпотентность | `GET /auth/me` отложен (`⏳`); повторная регистрация — 500                                                         |
| CORS            | `⬜` не настроен: браузерный frontend с другого origin пока не сможет обратиться к сервису                         |

Тело запроса и ответа ДОЛЖНО быть валидным JSON. Аутентифицированные маршруты ДОЛЖНЫ принимать токен в
заголовке `Authorization` по схеме `Bearer`. Тексты ошибок ДОЛЖНЫ быть на английском (`AGENTS.md` §7).

## 3. Схемы данных

Схемы объявлены в `src/api/auth/schemas.py`. Тела запросов и `AccessToken` привязаны к маршрутам и видны
в OpenAPI (Swagger UI `/docs`, ReDoc `/redoc`); `UserData` — модель ответа регистрации, см. §3.4.

### 3.1. `RegisterRequestBody` — тело запроса на регистрацию

| Поле       | Тип    | Обязательное | Ограничения                                                                    |
| ---------- | ------ | ------------ | ------------------------------------------------------------------------------ |
| `username` | string | да           | 3–30 символов, начинается с латинской буквы, далее латиница, цифры, `_` и `-`  |
| `email`    | string | да           | Валидный email; контакт для связи, для входа НЕ используется                   |
| `password` | string | да           | 8–72 символа; хотя бы одна строчная буква, заглавная буква, цифра и спецсимвол |

```json
{
  "username": "stalker_2010",
  "email": "user@airsoft-prim.ru",
  "password": "Str0ng!Pass"
}
```

Email в теле регистрации обязателен, но логином не служит: адрес нужен для связи и для сброса пароля
(`docs/API_PASSWORD.md`), а вход выполняется по `username` (§3.2, `docs/DOMAIN.md` §6.2).

Политику пароля проверяет валидатор схемы `RegisterRequestBody.validate_password` — одно регулярное
выражение `PASSWORD_REQUIREMENTS` с классами символов в нотации POSIX: `[:lower:]`, `[:upper:]`,
`[:digit:]` и `[:punct:]`. При несоответствии сервис ДОЛЖЕН вернуть 422 с общим сообщением
`Password does not meet the security requirements.`: оно НЕ ДОЛЖНО раскрывать, какой именно класс
символов отсутствует. Классы — ASCII, как в POSIX: пароль без латинских букв требованиям не отвечает. На
`LoginRequestBody` валидатор НЕ ДОЛЖЕН распространяться: вход не должен отклонять пароли, заданные до
включения политики. Длина ограничена символами (8–72): пароли хеширует Argon2id, у которого предела длины
входа нет, — поэтому отдельной проверки в байтах (как у bcrypt) не требуется (`docs/DOMAIN.md` §7.1).

### 3.2. `LoginRequestBody` — тело запроса на вход

| Поле       | Тип    | Обязательное | Смысл                |
| ---------- | ------ | ------------ | -------------------- |
| `username` | string | да           | Логин учётной записи |
| `password` | string | да           | Пароль               |

Email в теле входа не принимается: адрес — контакт для связи, а не логин (`docs/DOMAIN.md` §6.2). К
`username` применяется та же политика, что и при регистрации (§3.1): иначе вход отклонял бы логины,
которые сервис принимал при регистрации.

### 3.3. `AccessToken` — ответ с токеном

| Поле           | Тип    | Значение                           |
| -------------- | ------ | ---------------------------------- |
| `access_token` | string | Подписанный JWT (алгоритм `EdDSA`) |
| `token_type`   | string | Всегда `Bearer`                    |
| `expires_in`   | int    | Срок жизни токена в секундах       |

Поля `access_token` и `token_type` совпадают с ответом на выдачу токена в OAuth2 (RFC 6749 §5.1), чтобы
при добавлении OIDC не пришлось менять контракт клиентов. `expires_in` содержит срок жизни токена в
секундах, как требует RFC 6749 §5.1. Срок жизни — 24 часа по умолчанию, настраивается
`SECURITY_ACCESS_TOKEN_TTL` (`docs/DOMAIN.md` §4). Refresh-токена в ответе нет: `⏳`
(`docs/DOMAIN.md` §8).

### 3.4. `UserData` — данные учётной записи

| Поле         | Тип      | Смысл                                 |
| ------------ | -------- | ------------------------------------- |
| `id`         | int      | Идентификатор учётной записи          |
| `username`   | string   | Логин учётной записи                  |
| `email`      | string   | Адрес электронной почты               |
| `role`       | string   | Роль: `admin`, `moderator` или `user` |
| `created_at` | datetime | Момент создания учётной записи (UTC)  |
| `updated_at` | datetime | Момент последнего обновления (UTC)    |

Схема описывает учётную запись так, как её видит владелец; набор полей ограничен тем, что сервис
действительно хранит. Поле роли в схеме называется `role`, а в ORM-модели — `system_role`. Хеш пароля,
признак блокировки и служебные метки в данные учётной записи попадать НЕ ДОЛЖНЫ.

Маршрут регистрации отвечает 204 без тела (§4.1), поэтому `UserData` не привязана ни к одному маршруту и в
OpenAPI не попадает.

### 3.5. Тело ошибки

Единой схемы нет: ошибки приложения отдают объект `message`/`details`, а валидация FastAPI (422) —
`detail` со списком ошибок.

| Поле      | Тип             | Смысл                                         |
| --------- | --------------- | --------------------------------------------- |
| `message` | string          | Краткое описание ошибки                       |
| `details` | string          | Детали, безопасные для показа клиенту         |
| `detail`  | string или list | Тело 422 от FastAPI: строка или список ошибок |

Сам сервис отвечает объектом (401, 403, 409, 500), отказ валидации (422) — список объектов FastAPI с
полями `type`, `loc`, `msg`, `input`. Тексты ошибок ДОЛЖНЫ быть на английском (`AGENTS.md` §7).

Ошибки безопасности (`SecurityError`) обрабатываются общими обработчиками приложения:
невалидный, просроченный или неподписанный токен даёт 403, а отказ выпуска токена (например,
недоступный keyfile) — 500. Тело этих ответов — `message` и `details`; внутренняя причина отказа
выпуска в ответ не попадает. Ошибки входа (`UserIdentificationError`, `UserAuthenticationError`)
отдают 401 с заголовком `WWW-Authenticate: Bearer`.

```json
{
  "message": "Authorization failed.",
  "details": "Provided credentials are invalid."
}
```

Точные формулировки пока не зафиксированы: `⬜` (см. §8, п. 3).

## 4. Маршруты

### 4.1. `POST /auth/register` — регистрация

Создаёт учётную запись портала.

- Аутентификация: не требуется.
- Тело запроса: `RegisterRequestBody`.
- Ответ 204: тело пустое — профиль созданной учётной записи не отдаётся (§3.4, §8, п. 1).
- Побочные эффекты: запись в `auth.users`, роль `user`, `pswd_hash` — Argon2id-хеш пароля.
- Логин и адрес проверяются на занятость до записи, роль `user` проставляет сама БД (значение по умолчанию
  колонки `system_role`), поэтому приложение её не передаёт.
- Подтверждение email не требуется (`⏳`, `docs/DOMAIN.md` §8).

| Код | Когда                                                    | Тело               |
| --- | -------------------------------------------------------- | ------------------ |
| 204 | Учётная запись создана                                   | —                  |
| 409 | `username` или `email` уже заняты                        | Тело ошибки (§3.5) |
| 422 | Тело не соответствует схеме, в том числе политике пароля | Ошибки FastAPI     |
| 500 | Отказ БД                                                 | —                  |

```bash
curl -X POST http://localhost:8000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username": "stalker_2010", "email": "user@airsoft-prim.ru", "password": "Str0ng!Pass"}'
```

Ответ 204 тела не несёт: профиль созданной учётной записи не возвращается.

Занятые учётные данные сервис отвергает ошибкой `UserAlreadyExistsError` с английской причиной
(`Username is already taken.` или `Email is already taken.`); общий обработчик приложения переводит её
в 409, поэтому маршрут сам коды не транслирует. Уникальность окончательно держат констрейнты БД
(`UNIQUE` по `username` и индекс по `lower(email)`): параллельные регистрации одного логина вторую
учётную запись не создадут.

Токен регистрация НЕ ДОЛЖНА выдавать: клиент входит отдельным запросом. Выдавать токен сразу (автологин)
— открытый вопрос `⬜` (§8, п. 1).

### 4.2. `POST /auth/login` — вход

Проверяет логин и пароль и выпускает access-токен.

- Аутентификация: не требуется.
- Тело запроса: `LoginRequestBody`.
- Ответ 200: `AccessToken`.
- Побочные эффекты: событие входа должно попадать в аудит (`⬜`, `docs/DOMAIN.md` §9.3).
- Учётная запись ищется по `username` (точное совпадение: уникальность регистрозависима,
  `docs/DOMAIN.md` §7.2); пароль сверяется с `pswd_hash`. Системная роль из учётной записи попадает
  в токен claim'ом `srl`.
- Признак блокировки (`disabled`) проверяется: заблокированная учётная запись получает тот же 401,
  что и несуществующая, — клиент не узнаёт, что пара логин/пароль верна.
- Сообщение об ошибке НЕ ДОЛЖНО раскрывать, существует ли учётная запись и что именно не совпало.

| Код | Когда                                                   | Тело               |
| --- | ------------------------------------------------------- | ------------------ |
| 200 | Токен выпущен                                           | `AccessToken`      |
| 401 | Неверный логин или пароль; учётная запись заблокирована | Тело ошибки (§3.5) |
| 422 | Тело не соответствует схеме                             | Ошибки FastAPI     |
| 429 | Антибрутфорс: `⬜` не реализован                        | —                  |
| 500 | Отказ БД или выпуска токена                             | Тело ошибки (§3.5) |

```bash
curl -X POST http://localhost:8000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username": "stalker_2010", "password": "Str0ng!Pass"}'
```

```json
{
  "access_token": "eyJhbGciOiJFZERTQSIsImtpZCI6ImF1dGgtMjAyNi0wOSJ9...",
  "token_type": "Bearer",
  "expires_in": 86400
}
```

Блокировка и неверные учётные данные неразличимы для клиента: оба случая дают 401 с одинаковым телом
и `WWW-Authenticate: Bearer`.

### 4.3. `POST /auth/logout` — выход

Завершает сессию пользователя.

- Аутентификация: требуется `Bearer`-токен.
- Тело запроса: нет.
- Ответ 204: тело ответа отсутствует.
- Отзыв токенов не реализован (`⏳`, `docs/DOMAIN.md` §9.2): выход означает удаление токена на стороне
  клиента, а сам токен остаётся действительным до истечения срока жизни. Каждый токен уже несёт `jti`,
  поэтому отзыв конкретного токена можно будет адресовать, когда появится хранилище отзыва.

| Код | Когда                            | Тело               |
| --- | -------------------------------- | ------------------ |
| 204 | Выход выполнен                   | —                  |
| 401 | Токен отсутствует или не принят  | Тело ошибки (§3.5) |
| 500 | Логика не реализована (заглушка) | —                  |

```bash
curl -X POST http://localhost:8000/auth/logout \
  -H "Authorization: Bearer <access_token>"
```

Эндпоинт существует, чтобы у клиента был единый способ завершить сессию, а у сервиса — место для отзыва
токена в будущем. Пока отзыва нет, тот же результат клиент получает удалением токена у себя.

## 5. Как контракт описан в коде

| Файл                      | Что содержит                                                              |
| ------------------------- | ------------------------------------------------------------------------- |
| `src/api/auth/routes.py`  | Маршруты `APIRouter(prefix="/auth")`; регистрация и вход реализованы      |
| `src/api/auth/deps.py`    | Зависимости маршрутов: сервис учётных записей, хешер паролей и сервис JWT |
| `src/api/auth/schemas.py` | Схемы запросов и ответов этого документа                                  |
| `src/api/auth/docs.py`    | Описания для OpenAPI (`RouteDocs`)                                        |
| `src/api/__init__.py`     | Подключение роутера слоя к `main_router`                                  |

Пользователя из заголовка `Authorization` маршруты пока не извлекают: общая зависимость `CurrentUser`
удалена, а единственный параметр `current_user` (`POST /auth/logout`) объявлен заглушкой с типом `Any`.
Регистрацию обслуживают `src/api/auth/deps.py` и `src/services/user.py`: маршрут передаёт сервису учётных
записей логин, адрес и пароль, сервис проверяет занятость и хеширует пароль перед записью. Хешер паролей
(Argon2id) общий для сервиса и собирается в `src/general/security.py`.

Вход обслуживают `get_user_service` и `get_encryption_service`: `UserService.login` ищет учётную запись,
сверяет пароль и возвращает её Id и системную роль, а `JWTEncryptionService.encrypt` подписывает токен и
кладёт роль в claim `srl`. `JWTDecryptionService` проверяет токены, но к маршрутам пока не подключён:
`logout` поднимает `NotImplementedError` и отвечает 500.

`iss`, `aud`, `sub`, `srl` (необязательный), `iat`, `exp`, `jti` — `✅` (`docs/DOMAIN.md` §4.2);
`POST /auth/login` выпускает токен.

## 8. Открытые вопросы

Требуют решения владельца проекта. Пока пункт не решён, фактическое поведение описано в §4–§6 и может
отличаться от целевого.

1. **Ответ на регистрацию**: нужен ли профиль в ответе — сейчас 204 без тела — или профиль вместе с
   access-токеном, чтобы клиенту не требовался отдельный вход?
1. **Заблокированная учётная запись** — `✅` решено: единый 401, чтобы не подтверждать, что пара
   логин/пароль верна. Проверка `disabled` выполняется при входе.
1. **Формулировки ошибок** — `✅` формат зафиксирован: `message` и `details`, для 422 — `detail`.
   Осталось зафиксировать точные английские тексты для 401 (`docs/DOMAIN.md` §7). Трансляция
   `UserAlreadyExistsError` → 409 реализована в общем обработчике.
1. **Антибрутфорс**: пороги и окно блокировки, код ответа 429 (`docs/DOMAIN.md` §9.4).
1. **Размещение паролей**: смена и сброс — `/auth/password/*` или отдельный слой `/password` (заготовка
   `src/api/password/` уже есть)?
