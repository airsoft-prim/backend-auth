# API слоя `/auth`: маршруты и схемы

> Статус: **черновик**. HTTP-контракт слоя `/auth` сервиса `backend-auth`.
> Маркеры состояния: `✅` — решено и подтверждено кодом, `🚧` — решение принято, реализация не завершена,
> `⏳` — решение принято, но отложено на будущие версии, `⬜` — открытый вопрос, требует решения
> владельца проекта.
>
> Назначение файла: маршруты, схемы и коды ответов HTTP-слоя аутентификации. Предметная область —
> `docs/DOMAIN.md`, правила работы с кодом — `AGENTS.md`.

## 1. Назначение и состав слоя

Слой `/auth` — точка входа для аутентификации пользователей портала: регистрация, вход и выход.
Слой отвечает за идентичность, но не за права на ресурсы портала:
потребители токена решают это сами, читая данные пользователя из JWT (`docs/DOMAIN.md` §1).

| Маршрут               | Назначение                              | Состояние                                   |
| --------------------- | --------------------------------------- | ------------------------------------------- |
| `POST /auth/register` | Создание учётной записи                 | `🚧` контракт объявлен, логика — заглушка   |
| `POST /auth/login`    | Проверка учётных данных и выдача токена | `🚧` контракт объявлен, логика — заглушка   |
| `POST /auth/logout`   | Завершение сессии                       | `🚧` контракт объявлен, отзыв токена — `⏳` |

Профиль владельца токена (`GET /auth/me`) — `⏳` отложен: маршрут убран из контракта и вернётся вместе
с реализацией. В OIDC ему соответствует `userinfo`.

Смежные поверхности, которые в этот слой не входят:

| Поверхность                          | Где живёт                                            |
| ------------------------------------ | ---------------------------------------------------- |
| Публичные ключи подписи токенов      | `GET /.well-known/jwks.json` (`src/api/well_known/`) |
| Смена и сброс пароля                 | `⬜` отдельный слой, заготовка `src/api/password/`   |
| Администрирование ролей и блокировок | `⬜` не реализовано                                  |
| Обновление токена (refresh)          | `⏳` отложено (`docs/DOMAIN.md` §8)                  |

## 2. Соглашения

| Параметр        | Значение                                                                                                    |
| --------------- | ----------------------------------------------------------------------------------------------------------- |
| Базовый префикс | `/auth`; в dev-окружении сервис слушает `http://localhost:8000`                                             |
| Формат обмена   | JSON: `Content-Type: application/json; charset=utf-8`                                                       |
| Аутентификация  | Заголовок `Authorization: Bearer <access_token>`, схема OpenAPI `HTTPBearer`                                |
| Токен           | JWT, подпись `EdDSA` (Ed25519), срок жизни 24 часа (`docs/DOMAIN.md` §4)                                    |
| Формат ошибки   | `{"detail": ...}`; тексты ошибок — на английском; у отказа валидации (422) `detail` — список ошибок FastAPI |
| Время           | UTC, формат RFC 3339                                                                                        |
| Идемпотентность | `GET /auth/me` отложен (`⏳`); повторная регистрация вернёт 409                                             |
| CORS            | `⬜` не настроен: браузерный frontend с другого origin пока не сможет обратиться к сервису                  |

## 3. Схемы данных

Схемы объявлены в `src/api/auth/schemas.py`. Тела запросов и `AccessToken` привязаны к маршрутам и видны
в OpenAPI (Swagger UI `/docs`, ReDoc `/redoc`); `UserData` пока не привязана ни к одному маршруту и в
OpenAPI не попадает — см. §3.4.

### 3.1 `RegisterRequestBody` — тело запроса на регистрацию

| Поле       | Тип    | Обязательное | Ограничения                                                                    |
| ---------- | ------ | ------------ | ------------------------------------------------------------------------------ |
| `username` | string | да           | 3–50 символов, начинается с латинской буквы, далее латиница, цифры, `_` и `-`  |
| `email`    | string | да           | Валидный email; он же логин при входе                                          |
| `password` | string | да           | 8–72 символа; хотя бы одна строчная буква, заглавная буква, цифра и спецсимвол |

```json
{
  "username": "stalker_2010",
  "email": "user@airsoft-prim.ru",
  "password": "Str0ng!Pass"
}
```

Политику пароля проверяет валидатор схемы `RegisterRequestBody.validate_password` — одно регулярное
выражение `PASSWORD_REQUIREMENTS` с классами символов в нотации POSIX: `[:lower:]`, `[:upper:]`,
`[:digit:]` и `[:punct:]`. При несоответствии — 422 с общим сообщением `Password does not meet the
security requirements.`: оно не раскрывает, какой именно класс символов отсутствует. Классы — ASCII,
как в POSIX: пароль без латинских букв требованиям не отвечает. На `LoginRequestBody` валидатор не
распространяется: вход не должен отклонять пароли, заданные до включения политики. Длину bcrypt в
72 байта пока никто не проверяет — вместе с хешированием `🚧`.

### 3.2 `LoginRequestBody` — тело запроса на вход

| Поле       | Тип    | Обязательное | Смысл                |
| ---------- | ------ | ------------ | -------------------- |
| `email`    | string | да           | Email учётной записи |
| `password` | string | да           | Пароль               |

### 3.3 `AccessToken` — ответ с токеном

| Поле           | Тип    | Значение                           |
| -------------- | ------ | ---------------------------------- |
| `access_token` | string | Подписанный JWT (алгоритм `EdDSA`) |
| `token_type`   | string | Всегда `Bearer`                    |
| `expires_in`   | int    | Смысл поля уточняется (§8, п. 9)   |

Поля `access_token` и `token_type` совпадают с ответом на выдачу токена в OAuth2 (RFC 6749 §5.1), чтобы
при добавлении OIDC не пришлось менять контракт клиентов. С `expires_in` расхождение: в RFC это срок
жизни токена в секундах, а в схеме поле подписано как временная метка инвалидации токена; что именно
передавать — целое число секунд или метку времени — открытый вопрос `⬜` (§8, п. 9). Сам срок жизни
токена известен: 24 часа (`docs/DOMAIN.md` §4). Refresh-токена в ответе нет: `⏳` (`docs/DOMAIN.md` §8).

### 3.4 `UserData` — данные учётной записи

| Поле         | Тип      | Смысл                                 |
| ------------ | -------- | ------------------------------------- |
| `id`         | int      | Идентификатор учётной записи          |
| `username`   | string   | Логин учётной записи                  |
| `email`      | string   | Адрес электронной почты               |
| `role`       | string   | Роль: `admin`, `moderator` или `user` |
| `created_at` | datetime | Момент создания учётной записи (UTC)  |
| `updated_at` | datetime | Момент последнего обновления (UTC)    |

Схема строится прямо из ORM-модели `User`, поэтому набор полей ограничен тем, что сервис действительно
хранит. Поле роли в схеме называется `role`, а в ORM-модели — `system_role`. Хеш пароля, признак
блокировки и служебные метки в данные учётной записи не попадают.

Модель ответа у маршрута регистрации пока не объявлена: `register_user` возвращает `None`, поэтому
`UserData` в OpenAPI не попадает, а ответ 201 описан ею только в этом документе (§4.1).

### 3.5 Тело ошибки

Отдельной схемы у ошибок нет — их формируют `HTTPException` и валидация FastAPI, тело — один ключ
`detail`.

| Поле     | Тип             | Смысл                                     |
| -------- | --------------- | ----------------------------------------- |
| `detail` | string или list | Описание ошибки: строка или список ошибок |

Сам сервис отвечает строкой (401, 403, 409), отказ валидации (422) — список объектов FastAPI с полями
`type`, `loc`, `msg`, `input`. Тексты ошибок — на английском (`AGENTS.md` §7).

```json
{
  "detail": "Invalid email or password."
}
```

Точные формулировки пока не зафиксированы: `⬜` (см. §8, п. 4).

## 4. Маршруты

### 4.1 `POST /auth/register` — регистрация

Создаёт учётную запись портала.

- Аутентификация: не требуется.
- Тело запроса: `RegisterRequestBody`.
- Ответ 201: `UserData` созданной учётной записи.
- Побочные эффекты: запись в `auth.users`, роль `user`, `pswd_hash` — bcrypt-хеш пароля.
- Подтверждение email не требуется (`⏳`, `docs/DOMAIN.md` §8).

| Код | Когда                                                    | Тело              |
| --- | -------------------------------------------------------- | ----------------- |
| 201 | Учётная запись создана                                   | `UserData`        |
| 409 | `username` или `email` уже заняты                        | `{"detail": ...}` |
| 422 | Тело не соответствует схеме, в том числе политике пароля | Ошибки FastAPI    |
| 500 | Логика не реализована (заглушка)                         | —                 |

```bash
curl -X POST http://localhost:8000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username": "stalker_2010", "email": "user@airsoft-prim.ru", "password": "Str0ng!Pass"}'
```

```json
{
  "id": 42,
  "username": "stalker_2010",
  "email": "user@airsoft-prim.ru",
  "role": "user",
  "created_at": "2026-09-24T12:00:00Z",
  "updated_at": "2026-09-24T12:00:00Z"
}
```

Токен регистрация не выдаёт: клиент входит отдельным запросом. Выдавать токен сразу (автологин) —
открытый вопрос `⬜` (§8, п. 1).

### 4.2 `POST /auth/login` — вход

Проверяет email и пароль и выпускает access-токен.

- Аутентификация: не требуется.
- Тело запроса: `LoginRequestBody`.
- Ответ 200: `AccessToken`.
- Побочные эффекты: событие входа должно попадать в аудит (`⬜`, `docs/DOMAIN.md` §10.6).
- Учётная запись ищется по `lower(email)`; пароль сверяется с `pswd_hash`.
- Сообщение об ошибке не раскрывает, существует ли учётная запись и что именно не совпало.

| Код | Когда                            | Тело              |
| --- | -------------------------------- | ----------------- |
| 200 | Токен выпущен                    | `AccessToken`     |
| 401 | Неверный email или пароль        | `{"detail": ...}` |
| 403 | Учётная запись заблокирована     | `{"detail": ...}` |
| 422 | Тело не соответствует схеме      | Ошибки FastAPI    |
| 429 | Антибрутфорс: `⬜` не реализован | —                 |
| 500 | Логика не реализована (заглушка) | —                 |

```bash
curl -X POST http://localhost:8000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "user@airsoft-prim.ru", "password": "Str0ng!Pass"}'
```

```json
{
  "access_token": "eyJhbGciOiJFZERTQSIsImtpZCI6ImF1dGgtMjAyNi0wOSJ9...",
  "token_type": "Bearer",
  "expires_in": 86400
}
```

Разделение 401 и 403 — решение `⬜` (§8, п. 2): код 403 сообщает клиенту, что пара логин/пароль верна, но
учётная запись заблокирована.

### 4.3 `POST /auth/logout` — выход

Завершает сессию пользователя.

- Аутентификация: требуется `Bearer`-токен.
- Тело запроса: нет.
- Ответ 204: тело ответа отсутствует.
- Отзыв токенов не реализован (`⏳`, `docs/DOMAIN.md` §10.2): выход означает удаление токена на стороне
  клиента, а сам токен остаётся действительным до истечения срока жизни.

| Код | Когда                            | Тело              |
| --- | -------------------------------- | ----------------- |
| 204 | Выход выполнен                   | —                 |
| 401 | Токен отсутствует или не принят  | `{"detail": ...}` |
| 500 | Логика не реализована (заглушка) | —                 |

```bash
curl -X POST http://localhost:8000/auth/logout \
  -H "Authorization: Bearer <access_token>"
```

Эндпоинт существует, чтобы у клиента был единый способ завершить сессию, а у сервиса — место для отзыва
токена в будущем. Пока отзыва нет, тот же результат клиент получает удалением токена у себя.

## 5. Как контракт описан в коде

| Файл                      | Что содержит                                                             |
| ------------------------- | ------------------------------------------------------------------------ |
| `src/api/auth/routes.py`  | Маршруты `APIRouter(prefix="/auth")`; тело — `raise NotImplementedError` |
| `src/api/auth/schemas.py` | Схемы запросов и ответов этого документа                                 |
| `src/api/auth/docs.py`    | Описания для OpenAPI (`RouteDocs`)                                       |
| `src/api/__init__.py`     | Подключение роутера слоя к `main_router`                                 |

Пользователя из заголовка `Authorization` маршруты пока не извлекают: общая зависимость `CurrentUser`
удалена, а единственный параметр `current_user` (`POST /auth/logout`) объявлен заглушкой с типом
`Any`. Логика внутри — заглушка: все три обработчика поднимают `NotImplementedError`, поэтому сейчас
каждый запрос к `/auth/*` завершается ответом 500.

`exp`, `iss`) — `⬜` (`docs/DOMAIN.md` §10.1).

## 7. Сводка кодов ответов

| Код | Когда                                                        | Маршруты            |
| --- | ------------------------------------------------------------ | ------------------- |
| 200 | Вход выполнен                                                | `login`             |
| 201 | Учётная запись создана                                       | `register`          |
| 204 | Сессия завершена                                             | `logout`            |
| 401 | Токен отсутствует или не принят; неверные учётные данные     | `logout`, `login`   |
| 403 | Учётная запись заблокирована                                 | `login`             |
| 409 | `username` или `email` уже заняты                            | `register`          |
| 422 | Тело запроса не соответствует схеме                          | `register`, `login` |
| 429 | Слишком много попыток входа: `⬜` не реализовано             | `login`             |
| 500 | Логика не реализована: сейчас так отвечают все маршруты слоя | все                 |

## 8. Открытые вопросы

Требуют решения владельца проекта. Пока пункт не решён, поведение зафиксировано в коде как заглушка и
изменится вместе с реализацией.

1. **Ответ на регистрацию**: отдавать только профиль (сейчас) или профиль вместе с access-токеном,
   чтобы клиенту не требовался отдельный вход?
2. **Заблокированная учётная запись**: отвечать 403 (сейчас) или единым 401, чтобы не подтверждать,
   что пара логин/пароль верна?
3. **Вход по username**: разрешать ли вход не только по email?
4. **Формулировки ошибок аутентификации**: зафиксировать английские тексты для 401 (`docs/DOMAIN.md` §7).
5. **Антибрутфорс**: пороги и окно блокировки, код ответа 429 (`docs/DOMAIN.md` §10.7).
6. **Размещение паролей**: смена и сброс — `/auth/password/*` или отдельный слой `/password`
   (заготовка `src/api/password/` уже есть)?
7. **CORS**: разрешить ли браузерному frontend обращаться к сервису с другого origin и с какими
   правилами.
8. **Версионирование**: оставить пустой префикс как сейчас или добавить версию (`/v1/auth/...`) до
   появления внешних потребителей API.
9. **`expires_in` в ответе на вход**: передавать срок жизни токена в секундах, как описывает RFC 6749
   §5.1, или метку времени инвалидации, как подписано в схеме?

> Файл живой: контракт меняется вместе с кодом — правь `src/api/auth/docs.py` и этот файл в одном
> изменении.
